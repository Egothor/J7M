# Managed POJO hosting — profile managed-v1

`ApplicationManager` supports ordinary application classes through an explicit, signed deployment profile. Existing requests default to the legacy lifecycle/injector path. Generated indexes and `ManagedContainer` can still be used locally without deploying or signing an artifact.

For deployment, the trusted operator supplies an activation request with `configuration["j7m.annotations.profile"] = "managed-v1"` and strict signed verification. Unknown profiles, unsigned verification, an explicit development verification profile, missing indexes and unsupported annotation behavior fail before application constructors. Signature checks run before provider loading. A verified repository record never substitutes for the manager's own signature verification.

Host setup may supply an immutable `PublicKeyTrustStore` through the additive `LocalApplicationRepository(root, clock, limits, signingTrust)` and `ApplicationManager(runtime, repository, limits, managedOptions, signingTrust)` constructors. Public keys come from the operator; a bundle cannot nominate its own trusted signer. Old constructors retain local development trust for compatibility. Signing and transport authentication are independent: configure authenticated transports and runtime authorization explicitly.

The application build uses the real `j7m-annotation-processor`. A public `@J7mApplication` POJO declares the manifest's group/name/version; it does not implement the lifecycle interface. `@J7mService` implementations use the same managed constructor/field/factory graph as other components, rather than a separate zero-argument construction path. Bootstrap and exported services must have one activation-scoped definition. The graph, supported metadata, exact export contracts and installed policy capabilities validate before component construction.

Only explicit `@RemoteMethod` signatures on the public business interface/implementation lineage are remotely callable. `@RemoteService` is export intent, not a public-method wildcard. `@LocalOnly` combined with `@RemoteMethod` on the same effective signature is an activation/compilation conflict. Overloads retain erased parameter and return identities; the wire envelope uses the public interface declaration even when the implementation has a covariant return. The runtime proxy checks the allowlist before generated direct dispatch. Generated adapters call the implementation within its own module, so its package need not be exported or opened.

`ManagedServiceContract` combines contract ID, positive contract version and the complete interface `ManagedMethod`. `ManagedMethod` alone is internal index metadata; index format is not a service version. `@J7mService.contractId` defaults to the manifest-declared interface binary name, and `contractVersion` defaults to 1. The host computes reserved export metadata `j7m.contract.id`, `j7m.contract.version` and `j7m.qualifier.fingerprint`; conflicting manifest values are rejected. These values are compatibility evidence and never grant caller authority.

`@NoRemoteExport` blocks automatic instance export on a service type. On a remote method result or parameter, the profile supports statically by-value scalar, registered-schema, byte-array and explicit `ObjectRef` types; unsupported callback-interface combinations fail instead of exporting implicitly. Existing explicit references are not revoked, and explicit runtime export remains subject to its normal authorization. Runtime schema DTOs require an explicit host-owned codec allowlist; this profile does not install a global mutable registry from application metadata.

Current-context injection uses host-registered `context.kind` bindings. Activation components use `ManagedProvider<Principal>` / `ManagedProvider<InvocationContext>` for `@CurrentPrincipal` / `@CurrentInvocation`; direct captures are permitted in an explicit CALL scope. `@CurrentApplication` may be a direct activation context or provider. Providers read the current dispatch snapshot rather than retaining the constructing caller. The runtime installs authenticated transport context for actual dispatch, opens a managed CALL scope and clears both scopes on normal return or exception. No field is reassigned concurrently between callers.

Public zero-argument `@Initialize`, `@Startup`, `@Drain` and `@Shutdown` methods use generated direct calls. Initialization/startup follow dependency construction order; drain/shutdown reverse it. Newly created CALL/PROTOTYPE objects inherit started lifecycle phases and dispose when their actual scope exits. Owned `AutoCloseable` objects close once, after other shutdown hooks. An annotated `AutoCloseable.close` is fulfilled by owned disposal rather than a second generated call. Borrowed values are not closed. Prepared providers can be read by cleanup callbacks, but cannot create new objects or resurrect a closed activation.

Drain closes admission. A managed stop while a handler is still running returns `success=false`, state `DRAINING`, and retains its resources and reference until actual completion. A later stop completes disposal; repeated successful stop does not repeat hooks. Upgrade/rollback checks the same actual invocation count atomically with its admission-state transition and returns an incomplete result while handlers are active. Managed lifecycle requests retain their activation profile/configuration, and rollback retains the previous activation's request rather than falling back to legacy construction. The cluster host also requires the manager's successful deactivation before installing a replacement, including direct ObjectRef callers outside its own alias counter. A timeout or disconnect is not proof that a handler stopped. Failed initialization/startup or partial export rolls back prepared exports, owned objects, host bindings and policy bindings once, with redacted diagnostics.

Trusted `ManagedHostingOptions` contains immutable bounded host capabilities. `ManagedHostBindings` selects exactly one primary attribute (`context.kind`, `service.name` or `resource.name`) and validates all metadata before binding/constructing. `ManagedInvocationPolicy` validates complete contracts before constructors, prepares owned per-export state and wraps generated dispatch. Every finite component also passes `validateComponent` before constructors. Non-exported components with claimed policy annotations are rejected by default; a real component adapter must explicitly validate/enforce them. Ordinary Java/self calls do not acquire managed invocation guards. Every continuation carries the actual runtime-allocated `ObjectRef` through `Proceed.target()`; caller arguments and contract IDs cannot replace the concrete resource identity. Optional security, retry and distributed adapters must implement and register real behavior; annotation presence alone installs nothing. These extension seams do not add retry, deduplication or backend dependencies to the base platform.

For JPMS hosting, run the host with its shared named `org.j7m.api` module, keep application modules separate and declare each generated index with `provides ManagedComponentIndex with ...`. A managed bundle cannot contain a replacement API module. Export the public business interface package for the transport; implementation packages may remain encapsulated. No blanket `opens` or reflection bypass is used. Legacy classpath/JPMS activation retains its existing behavior.

Rollback before adoption removes the managed profile/index wiring and restores the previous artifact. After managed deployment, drain and stop the actual activation before restoring a previous signed compatible artifact; do not switch a running instance's construction model in place.

Author checks include real javac adapters, owned CALL lifecycle, failed startup, host capability rejection, unsigned/untrusted signer rejection and separate-JVM classpath/JPMS signed hosting over mTLS. Parallel callers use distinct certificate principals. The tests verify denied overloads, actual policy target references, no implicit callback export, exception redaction, held-handler drain and cleanup. They are ordinary bounded tests, with no hourly soak dependency.

## Open A-P17 acceptance dependency: scoped schema codecs

Automatic loading of verified application `SchemaIndex` providers into actual RPC exports still requires a trusted host-only per-export codec registration keyed by the concrete `ObjectRef`. It must retain the existing codec context for callbacks, use the verified application allowlist and unregister on failed activation/unexport to release class loaders. Client DTOs keep an explicit client-owned schema setup. A `ValueCodec` must not be inserted into wireable `ExportOptions`, where it could become a remote callback. This is an explicit remaining A-P17 dependency, not a claim that managed hosting already installs per-application schemas.

Managed operational probes use generated direct adapters for public zero-argument methods returning primitive `boolean` on ACTIVATION components. `@HealthCheck` and `@ReadinessCheck` do not add remote methods. Legacy health-check result conventions remain unchanged. Runtime validation compares generated probe identities with actual class/interface annotations before construction, including deployments compiled without annotation processing.

The manager automatically samples every declared probe through a bounded host-owned monitor. `ManagedHostingOptions.probeSettings` configures physical worker capacity, activation capacity, sampling interval, total observation budget and freshness; the compatible two-argument constructor selects the development defaults (4 workers, 64 activations, 100 ms sampling/budget, 2 s freshness). `probes(instanceId)` exposes generation-bound host handles; `probeStatus(instanceId)` reads cached observations without invoking application code. Probe execution uses an anonymous, unauthenticated security context with no host administration roles. It receives application identity but inherits neither a deployment operator nor a remote caller.

A declared readiness probe starts the prepared export as not ready before publication. Only fresh successful observations admit traffic; readiness expires without a fresh observation. Failed readiness excludes discovery and rejects direct calls through the actual owned registration. Without a declared readiness probe, ordinary managed hosting retains its existing export behavior; deployment/canary readiness still requires an explicit verified readiness signal. Health-only probes are sampled for operational observation and do not close the traffic gate.

Drain detaches sampling and rejects new probes. An already executing probe continues to count as physically in flight until its method exits, including after an observation timeout or advisory cancellation. A blocked probe therefore keeps drain incomplete; no timeout is evidence that application code stopped. Late observations cannot reopen a drained or replaced activation. Direct Java calls and self-invocation are outside this host probe boundary.

Kernel readiness is an opt-in control on the owned prepared/committed registration handle. It preserves object identity and permits read-only reference validation while unready, so an existing proxy can recover after a later positive observation. Business dispatch always checks the current server-owned monotonic expiry, regardless of caller-supplied reference metadata or a stalled heartbeat. Controlled local lookup uses a proxy rather than handing out a raw target. Previously obtained ordinary Java references remain outside middleware admission.

The `j7m.readiness.*` metadata namespace is reserved to the host; application export options and managed manifest entries cannot assert it. Readiness changes update local admission immediately and coalesce asynchronous registry publication to one pending task per object. Registry calls run outside activation/publication monitors. Remote discovery changes converge after publication; cached or delayed discovery hints never override the server gate. Current metadata is republished by controlled heartbeats without renewing the observation deadline. Late publication after unexport removes the obsolete record. Publication errors increment `RuntimeStatus.security().get("readinessPublicationFailures")` without exporting exception details; subsequent observations or heartbeats retry.

Registry readiness publication admits at most 1,024 queued or physically executing tasks per runtime, including tasks retained for closed export generations; repeated observations of one object coalesce. Saturation defers publication instead of blocking the observer or growing this queue. Local admission and expiry remain authoritative, and a later observation/heartbeat retries. `readinessPublicationPending` and `readinessPublicationDeferred` in `RuntimeStatus.security()` expose the actual occupancy and cumulative deferrals. This bound covers the readiness publication path, not arbitrary application payload allocation or other scheduler work.
