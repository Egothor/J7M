# Managed component container, format1

`ManagedContainer` is an opt-in activation API over finite generated `ManagedComponentIndex` providers. It is independent of `DefaultJ7mInjector` and the existing manifest/ApplicationManager lifecycle. This implementation does not yet host annotation-only applications (A-P03), propagate invocation/principal context across async work, or refresh service/resource routing (A-P05).

The A-P01 JSR269 processor emits direct-access component indexes. A caller passes an explicit collection to `ManagedContainer.activate(indexes)` or explicitly loads the declared `ManagedComponentIndex` module service. There is no classpath scan. Version1 is required, with at most1024 definitions and256 dependency edges per definition; full method metadata preserves overloads. Public generated helpers use ordinary member access, without global JPMS opens. An index is executable trusted application code, not an untrusted-data sandbox. The host still authorizes artifacts and capabilities.

The complete dependency graph is validated before component construction: missing and ambiguous keys, duplicate definitions, lazy and direct cycles, unsupported metadata, and activation capture of CALL through a direct prototype chain are rejected. Selection uses assignable contract type, exact name and the complete qualifier set. There is no managed unnamed fallback. Legacy injection, including its Named fallback and injection-time context snapshots, is unchanged.

`@J7mComponent.name` and type-level `@Named` normalize to one name; different nonempty names conflict. Custom runtime-retained annotations marked `@Qualifier` are identified by binary type and all member values, including defaults. `ManagedQualifier.value` is the shared compiler/runtime canonical encoder. It supports primitive/string/enum/class members and bounded arrays; nested annotation member values are unsupported. `@Produces(name=..., ownership=...)` names a factory product without changing existing Named targets. Constructor dependencies are resolved before direct generated field injection. A factory receiver is a normal declared dependency with its own independent scope and ownership.

## Scope and ownership

| Scope | Instance identity | Owner and disposal |
| --- | --- | --- |
| ACTIVATION | Eager single instance per definition and container | Activation owns OWNED results until container close. |
| CALL | One instance per explicit CallScope | The call owns OWNED results and closes them when idle. |
| PROTOTYPE | New instance per resolution | Resolving activation or call owns the result; this is explicit rather than caller-detached ownership. |

`ManagedProvider<T>` delays resolution; it does not capture the call which created it. `CallScope.call(Callable)` establishes the active scope on the current thread and restores thread state on exit. `CallScope.get` establishes that scope during construction. To invoke an activation component that reads a CALL provider, execute the invocation inside `CallScope.call`. No call is inherited by new threads or CompletionStages. A call scope may move serially between threads; concurrent use or nested different calls in one container is rejected. Different call scopes can execute concurrently.

Owned results are tracked by object identity and disposed in reverse creation order exactly once through AutoCloseable, even when two definitions return the same identity. A borrowed alias does not acquire ownership. An owned identity cannot be owned by two different scopes. BORROWED factory results remain the supplier's responsibility and must outlive borrowing scopes. Lifecycle Shutdown hooks belong to A-P03 and are not also invoked here. A constructor which throws before returning an object must clean up its own internal resources; the container can dispose only successfully returned products and resolved dependencies.

Creation or field-injection failure invalidates the resolving ownership scope and disposes its returned owned products/dependencies. An activation failure prevents publication of the container. Disposer exceptions are reported by safe aggregate codes, remaining disposers still run, and repeated close never retries disposal. Closing a running call/container is rejected as CALL_BUSY; the caller drains actual work and closes again. This is not cancellation or automatic undo. Keep raw references within their owning lifetime.

Default capacity is4096 uniquely owned live instances and separately4096 open calls; an explicit1..1000000 capacity can be supplied. There is no unbounded prototype retention hidden from that limit. `status()` exposes aggregate definitions/open calls/owned instances/creation and failure counts without qualifier, config or payload labels. `Failure.code()` is a stable category. `Failure.diagnostic()` carries the actual missing/ambiguous/cycle/scope/construction path, bounded to32 class names and4096 characters. It contains no qualifier/configuration values or application exception messages. Managed activation preserves this evidence as `ManagedInjectionException.diagnostic()`; failed activation status includes `injection.reasonCode`, `injection.component` and `injection.graphPath`. JPMS public service contracts must be exported to the kernel module; failure is reported before component construction. Generated direct adapters and schema codecs do not require opening application implementation packages.

## Configuration and future refresh

The additive `activate(indexes, capacity, liveConfiguration)` overload borrows a host-owned LiveConfiguration and owns only its ConfigBinding registrations. Bindings validate before component construction; failed activation and container close detach all registrations without closing the host owner. Generated scalar metadata uses config.key/default/required/refresh; record metadata uses config.prefix/refresh. Only exact supported attribute sets and boolean spellings are accepted. Configuration qualifiers/names cannot be mixed with these bindings. Refresh requires ManagedProvider; direct injection uses a stable initial value, never concurrent field reassignment. Optional scalar configuration can explicitly produce null according to LiveConfiguration's contract.

Dependency attributes also reserve the finite adapter seam for A-P05; active unsupported routing/refresh metadata is rejected rather than silently treated as working failover. Current Provider is a scoped lookup, not a topology proxy. Configuration updates are whole-snapshot operations owned by LiveConfiguration; the container adds no network watcher of its own.

## Validation and compatibility

Author tests cover strict graph selection, all three lifetimes, concurrent calls/provider cleanup, factory failure, owned/borrowed aliases, disposal failures, bounds, safe metadata and actual JSR269-generated creators/fields/factory products. The latter compiles real source, loads its generated service indexes and executes public APIs; separate A-P01 JPMS/schema tests establish their own module/codec boundary. Their results must be recorded by the author and independently reviewed; this guide itself is not a PASS assertion.

Rollback before use removes the new opt-in API/index dependency and preserves legacy injection. Closing an activation releases its owned resources and config registrations. No durable format changes are made; reverting after use must still close live activations and retain caller-owned/borrowed resources. Do not claim A-P03/A-P05 implementation from the existence of this container.
