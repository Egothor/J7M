# Managed transaction boundaries

A-P11 adds two distinct METHOD annotations selecting finite trusted host policies. An annotation does not install a backend, convey coordinator credentials or create ambient transaction authority. The optional module retains the existing application-platform boundary: legacy hosting does not acquire a dependency on distributed consensus or a JDBC driver.

| Annotation | Host policy | Actual protocol |
|---|---|---|
| `@ResourceTransaction(policy="default")` | `ManagedResourceTransactionPolicy` | Existing D7 strict-2PL/2PC over registered resource groups |
| `@JdbcTransaction(policy="default")` | `ManagedJdbcTransactionPolicy` | One owned H2 TCP Connection, local DB transaction |

Both policies use the fixed TRANSACTION phase. SECURITY, OBSERVATION, ADMISSION, OWNERSHIP and REPLAY precede it. Result finalizers unwind in reverse order after actual tracked USER settlement: transaction completion precedes durable result caching and outer audit. Connection/context disposal does not release the surrounding CALL/physical invocation before kernel encoding exits.

## Admission and REQUIRED ownership

Host registrations are immutable maps with at most256 ASCII policy IDs of at most64 characters. Unknown policies, conflicting effective interface/implementation annotations and unsupported mixed protocols reject before application construction. The runtime still requires an explicitly installed host policy when annotation processing was disabled. No default capability grant was added to RuntimeContracts.

An invocation must have actual owned USER scope, result-finalizer support and explicit `findContext` support. The policy installs a pending context and finalizer **before** native BEGIN or connection opening. Unsupported scope/attachments cannot create a ghost transaction. A factory is responsible for its own allocation failures before returning a resource; a connection returned to the policy is then owned and closed on every admitted failure path.

REQUIRED joins only the exact current owned context and the same named registration instance. It does not open a second transaction/connection or install a second completion callback. A nested intercepted failure is sticky rollback-only even if the outer method catches it. A different profile or protocol rejects before another begin/open and marks the existing transaction rollback-only. Missing keys produce Optional.empty only inside an actual valid owner CALL; invalid/closed contexts throw and are never interpreted as absence.

A call through another ObjectRef has its own invocation and no ambient transaction permission. Ordinary Java self-invocation introduces no interception: it uses the already active outer context. An error propagated to the outer boundary causes rollback; an error swallowed by ordinary Java code requires explicit `setRollbackOnly()` when rollback is desired. REQUIRES_NEW, savepoints, XA and transaction propagation through caller metadata are unsupported.

## Native resource 2PC

`ManagedResourceTransactionPolicy.Registration` borrows one authorized coordinator endpoint and1–64 named participant endpoints. Participants must represent independent native resource groups; the registration rejects obvious reference aliases to the coordinator or another participant. Different endpoint wrappers do not prove different groups: the trusted host must configure their actual independent identities correctly. The policy never closes borrowed native clients.

`ResourceBindingFactory.resourceTransactionContext()` registers provider-only lookup of `ManagedResourceTransactionContext`, normally under a host-selected transaction resource name. Its methods are `transactionId()`, `read(participant,key)`, `write(participant,key,value)`, `lockRange(participant,prefix)`, `setRollbackOnly()` and `rollbackOnly()`. The opaque ID permits an authorized host to use existing native `RecoverableTransactions.status/recover/recoverPrepared/abort`; it is not a bearer credential.

Reads durably enlist the participant and acquire native locks before returning the authoritative value/version. Repeated reads use the protected observed value. Read-your-writes returns the staged value with its observed pre-commit version. Writes remain local until prepare/commit. Range locks use the existing conservative tenant-wide native predicate lock; no separate range-query or snapshot parser was introduced.

One context admits at most64 first read/write/range operations and256KiB of key/prefix/value text in modified UTF. A first write also performs a first locked read, so32 new written keys consume64 operations. Replacing an existing staged write does not allocate another operation. Keys are nonblank and at most128 characters; prefixes may be empty, at most128 characters; NUL and reserved `*` are rejected. Values have at most16384 characters without NUL. Inputs and the final per-participant operation lists are copied/frozen. Native request/journal/storage limits remain in force; hosts must provision and preserve recovery headroom. Capacity or unavailable authority produces a truthful failed/in-doubt outcome, never an automatic new transaction or a heuristic decision.

After USER seal the finalizer prepares each durably enlisted participant, then invokes the existing coordinator commit/recovery protocol. A call with no participating operations closes the native record as ABORTED/NO_EFFECT while preserving its ordinary logical value; it does not invent an empty resource COMMIT. A known pre-decision application failure or exhausted original budget uses authorized abort cleanup. An unavailable coordinator or uncertain prepare/decision leaves IN_DOUBT and durable locks retained. A committed decision is never undone by reply timeout or by a later request to abort. Recovery replays only the authoritative decision and retains native delivery identities. Cleanup is bounded by the configured positive budget, at most30seconds; it cannot authorize a new business COMMIT.

## One local H2 TCP transaction

`ManagedJdbcTransactionPolicy.Registration` borrows a fresh-connection factory and a positive cleanup budget up to30seconds. The only qualified profile is **H2 TCP2.3.232**, using SERIALIZABLE isolation and a fresh independently owned autocommit connection. Embedded H2, other versions/vendors, an already non-autocommit connection and vendor-specific extensions are not silently accepted. Production supplies its driver, authentication and connection factory; H2 is a test dependency, not an imposed production driver. Driver connection establishment timeouts remain host configuration.

`ResourceBindingFactory.jdbcConnection()` supports `@J7mResource` with `ManagedProvider<java.sql.Connection>`. It returns the exact stable guarded Connection of the current transaction, not a global proxy selecting different physical connections. `jdbcTransactionContext()` alternatively exposes `ManagedJdbcTransactionContext` for `connection()`, `setRollbackOnly()` and `rollbackOnly()`. All three transaction registrations are provider-only, NEVER selection; neither activation-time direct capture nor ownership refresh is supported.

Application SQL and existing `JdbcDelivery` inbox/outbox calls use the same guarded Connection. The host alone configures, commits, rolls back and closes its physical connection. USER access cannot invoke commit/rollback/close/abort, autocommit, isolation/read-only/schema/catalog/client/network configuration, savepoints, nativeSQL, prepareCall or unwrap. Standard Statement/ResultSet close remains idempotent and works in an actual USER finally block after cancellation. Backlinks from statements/results/metadata return guarded objects; metadata URL/user diagnostics are redacted. The host closes remaining handles and the connection even when another cleanup fails.

The deliberately finite H2 data subset accepts bounded SELECT/INSERT/UPDATE/DELETE/MERGE statements. Maximum SQL length is16384 UTF-16 characters and4096 lexical tokens. Comments, multiple statements, JDBC escapes, DDL, transaction/procedure commands and unknown/quoted/qualified function calls are rejected before driver execution. Supported unqualified functions are COUNT, SUM, MIN, MAX, AVG, COALESCE, UPPER, LOWER, LENGTH, OCTET_LENGTH, ABS, ROUND and CAST. Supported datatype/grouping forms are finite; this is not a SQL/Java sandbox or an arbitrary dialect claim.

The guard retains at most256 JDBC handles per invocation lifetime, including closed handle identities, and at most128 batch additions. Result sets are forward-only/read-only and report an explicit error on a1025th row rather than silently truncating at1024. Live LOB/stream/array/ref/JAVA_OBJECT values and vendor unwrapping are unsupported; supported detached getters include ordinary scalar/date/time/byte values. Application code must detach results before USER seal; a codec cannot fetch more SQL or use a retained JDBC handle afterward. Declared live java.sql return types fail preflight.

Statement query timeout is clamped to the original remaining invocation budget and at most30seconds, preserving any stricter positive application timeout. Zero means the bounded host limit; negative values reject. The driver network timeout is also bounded. On expiry/cancellation no new COMMIT starts from a fresh cleanup budget. Rollback/close may use the separate cleanup budget; it never extends a business operation. A commit already initiated may remain UNKNOWN if its reply fails. Noncooperative driver work retains actual physical ownership until exit; timeout does not fabricate disposal or proof of rollback.

Successful USER settlement commits; propagated failures and sticky rollback-only roll back. A caught nested failure cannot turn rollback-only into success. A failed commit reply remains UNKNOWN even if the DB in fact committed. There is no blind commit replay. Errors leaving the host use normalized safe outcomes, not driver SQL text, causes, credentials or arbitrary application diagnostic details.

## Composition and recovery limits

Native resource 2PC and local JDBC cannot participate in the same invocation. D12 protected map CAS also cannot be combined with either transaction domain. The prohibition is installed before begin/open; a caught illegal CAS attempt still marks the transaction rollback-only and prevents a cached success. Already staged D12 effects prevent opening the other transaction. No callback, thread-local registry or public context writer was added.

Cache-only `@Deduplicated` wrapping is supported. The transaction commits before D12 caches its result. A crash or result-cache failure between these decisions is explicitly UNKNOWN and does not automatically reenter the body. This is not a single atomic transaction across DB/resource groups, D12 and a queue. Inbox/outbox rows join only their actual JDBC connection; remote relay/send/ack remains a separate recoverable protocol step.

Rollback before use removes additive policies/annotations. After use preserve native transaction journals, prepared locks, DB schemas and D12 retained identities. Stop admission and resolve/recover outstanding transactions before retiring a profile. Never erase an in-doubt record or reinterpret a durable COMMIT as aborted. No native storage format or existing backend implementation changed for A-P11.

## Executed qualification

`ManagedJdbcTransactionIT` uses actual H2 TCP and the real production invocation lifetime. It covers one guarded connection for application/inbox/outbox writes, commit/rollback, nested rollback-only, async child/finally retention, cancellation/expiry, API/SQL escape guards, explicit row/handle limits, allocation/cleanup failures, uncertain committed outcomes and cache-only/mixed-CAS behavior. `JdbcDataSqlTest` verifies the declared syntax bounds and allowlist. `ManagedResourceTransactionTest` uses actual native state machines for strict locks, frozen operations, retained decisions and capacity boundaries; `ManagedTransactionCompositionTest` covers the D12 boundary explicitly.

`ManagedTransactionProcessIT` compiles a real annotated application with J7mProcessor and loads its generated index into ManagedContainer with actual provider bindings. Dispatch uses the generated ManagedHostAdapter and production lifetime/policy SPI. Three separate durable **one-voter groups** host the coordinator and two participants, plus a separate frontend JVM. The gate kills the frontend after prepare and after durable decision, kills/restarts the coordinator and then every backend, verifies preserved locks/IN_DOUBT, committed delivery and version-stable recovery. It does not claim three-voter or nine-JVM quorum qualification; that tolerance is inherited from the independent D gates. A separate actual H2 TCP test kills the frontend immediately before and after the real driver commit. Synthetic loopback credentials and the test-owned host composition do not constitute production TLS or signed ApplicationManager deployment; combined deployment belongs to A-P17.
