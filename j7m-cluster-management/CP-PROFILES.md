# Versioned CP deployment profiles

`CpDeploymentProfile.DEVELOPMENT_LINUX_JAVA25_CP3_V1` and `DEVELOPMENT_LINUX_JAVA25_CP5_V1` are reusable packaged configuration factories. Version1 targets Linux, Java25 and local durable disks with file/directory fsync and atomic rename. Supply an explicit roster of exactly3 or5 authorized voters, node identity, exclusively owned per-node storage directory, secret, mutual TLS context and stable group generation. There is no implicit discovery, hostname, embedded key or automatic voting change. Existing directories are accepted for normal restart; the node validates durable identity and exclusive ownership. Recovery uses a fresh generation through `ConsensusBackup`, not an overwritten live directory.

Both factories set a500ms minimum election timeout,20ms heartbeat interval,1MiB maximum frame and128MiB maximum application snapshot. Qualification assumes measured clock uncertainty at most500ms and recovery within30s once a sufficient quorum returns. These values are assumptions and acceptance thresholds, not runtime measurements or an accepted production SLO. Configure the measured-time provider and clock admission checks separately. A three-voter group needs two voters; a five-voter group needs three. Majority loss refuses new authoritative work. Endpoints outside loopback require caller-provisioned mutual TLS; loopback-only null TLS still uses authenticated frames.

Construct one configuration per roster member with `profile.configuration(nodeId, authorizedVoters, perNodeDirectory, secret, tlsContext, groupId)` and pass it to the normal `NetworkConsensusNode`/host API. Protect the supplied secret and use a distinct group ID for each independent group and fresh recovery generation. The returned configuration copies its roster and secret; the profile does not start or orchestrate nodes. The exact-size roster intentionally excludes learners; use the lower-level configuration and membership APIs for a different topology instead of silently changing this versioned qualification profile.

Resource-service replay admission is a separate bounded transport setting, not a Raft profile field. The compatible `RemoteResourceServer` default remains8192 retained nonces. The D17 management qualification load explicitly provisions65536 through its configurable constructor; use an explicit capacity that fits the authenticated request/replay window and memory budget. Increasing it is not a retention or concurrency guarantee for application resources.

Focused tests create actual TCP quorum groups from both factories and verify committed work and durable restart. The separate D18 hour soak uses equivalent explicit settings in its process fixture; the factory itself is **not** claimed to have participated in that retained hour run. See [recovery contract and acceptance commands](../j7m-consensus/RECOVERY.md). The factories are additive and removable before use; after durable use preserve the configuration generation and snapshot compatibility on restart or use a deliberate recovery migration.
